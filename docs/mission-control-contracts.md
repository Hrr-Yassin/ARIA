# ARIA Mission Control 2.0 frontend contracts

The audit started from local revision `99060056c863affba4935fb98da5950a0ed1f5b9` with a clean index and worktree. The earlier interface foundation and route inventory are in `docs/aria-phase-a-architecture.md` and `docs/phase0-route-inventory.csv`. This matrix records the contracts consumed by Mission Control in addition to those historical inventories.

The original dashboard made 19 API requests for a selected session on initialization. It requested chat restore, full decision entries and duplicated campaign and finding information whether or not the relevant panel was open. Its accounting coercion turned absent or null values into zero. In the headed baseline, 5 call reservations remained, but 3,926 tokens could not cover the 8,192-token minimum. The budget panel gave no explanation and presented a missing campaign accounting summary as three zeros. The workspace and dashboard had separate fetch loops and independent session selection.

## Common semantics

All routes are same origin. Authenticated reads accept the existing bearer or HTTP-only cookie rules. Existing state-changing routes require a bearer and recheck server ownership. 401 redirects to sign-in and clears the stored identity. 403 and 409 are access or state denials. Network, invalid-schema and 5xx responses have a distinct unavailable state. Previously received data for the same session can remain visible with the retrieval time and a stale label. Campaign health alone treats an owner-scoped 404 from its contract as the absence of a campaign.

## Design and known limits

FastAPI serves the app. Vite compiles locally from pinned npm packages and TypeScript checks the shared session store, visualization boundaries and API shapes. Route-level dynamic imports keep the graph and chart libraries out of the Overview entry point. The existing research chat and the prior dashboard have separate compatibility URLs. The dashboard becomes Mission Control when the bundle is present.

The event and operations APIs serialize explicit public fields. Events link through stored identity, dependency, or evidence references. The authorization journal reads up to 100 durable registration, approval, rejection, or claim events. It uses the stored action ID to connect records for the same proposal. The journal omits actor identities, commands, scope hashes, and free-form decision metadata. A claim records consumption of authorization. Worker outcomes come from the receipt source. The current review queue comes from the live run projection. Each campaign retains up to 50 ring records. The archive can open earlier rows while Overview, Operations and Analytics continue using the current campaign source. Team history can extend beyond the selected browser window, and worker receipts can omit intermediate states. The browser reports retention gaps and source failures independently. A live refresh follows at most four forward pages through their authoritative cursors. Events labels a remaining backlog and the next refresh resumes from the last accepted cursor. A stalled cursor ends the refresh with a visible error and preserves previously accepted records.

Replay captures the currently available session records or selected campaign ring in browser memory. Search and source filters operate on the captured records. Live updates continue in the background and appear after leaving replay. Access denial or session change removes the snapshot and closes the inspector. Source bounds still apply, and events discarded by a producer's retention window remain unavailable.

Admission uses the server's conservative empty-input floor. It can identify a definite blocked state, and remaining capacity alone leaves full-request admission undetermined. Tariff prerequisites refer to the configured selection. Provider availability, actual request size, scope, campaign/task ledgers and reservations at admission can still change feasibility. Capabilities and transport performance have independent provenance. The response includes closed outcome codes, numeric timings, and the recorded OpenRouter charge when available. Raw exceptions, owner identity, tariffs, and other provider receipt fields remain outside the Mission Control payload.

Command history is process-local. The projection returns HTTP status where found and receipt metadata where retained. Operations also reads grouped durable web replay states bound to both session owner and requester. It returns only stored record, pending cancellation and unknown outcome counts; it reads no protected specifications, responses or capture content and never contacts the connector. This independent source can be unavailable without hiding receipts or authorization history. Pending replay termination remains visible after reload. Arbitrary output and command arguments can contain operational or credential material and are excluded. Receipt creation time is not proof of worker runtime. The app displays installed, advertised and healthy states only where a source supports them.

The shell supports observation, session bookkeeping, review, containment and explicit campaign resume. Workspace reuses the existing research document inside the selected-session shell rather than replacing its chat, Auto, approval and settings handlers. Those existing controls retain their API authorization and financial limits. Only existing records and isolated stores are used for graphical acceptance; no inference, active target execution or VM provisioning is needed. Live execution outcomes require separate admissible authorization and budgets.

Workspace is loaded only when selected. It shares the shell's owner-session selection and theme/accent palette. Shell refresh and mode changes preserve its draft and document identity; leaving the view or changing sessions releases the child document, its timers and sockets. Observation panels can be collapsed persistently; containment and pending approvals remain visible. Inspector width is keyboard adjustable and persisted. A stop acknowledgement with pending worker or web replay termination is visibly unconfirmed. Post-mutation reconciliation waits for older in-flight reads before fetching new server records.

The refresh screenshot comparison retains both exact hashes and actual pixel differences. On this GPU, curved avatar edges varied on 19 pixels by at most 2/255 per channel. The visual-stability test therefore permits only a 2/255 channel delta on at most 0.01% of pixels; text or layout movement still fails. Original failed captures are retained. Actual 603-record timeline scrolling is measured separately from render-only benchmarks. Process RSS measurements sum resident pages per process and include shared pages multiple times; they do not claim unique browser memory.

## Build and verify locally

Use Node 20.19 or newer in the Node 20 line, or Node 22.12 or newer. Build output belongs in the ignored `web/static/mission/` directory. FastAPI resolves `/dashboard` to that bundle. `/dashboard/legacy` is the compatibility overview, and `/chat/{id}` remains the existing research chat. A clean checkout without the bundle serves the compatibility overview until the build is present. Sign in directly at `/login?next=mission` to open the new overview.

```sh
npm --prefix web/mission-control ci --ignore-scripts
npm --prefix web/mission-control run build
.venv/bin/python -m unittest discover -s tests -t . -q
node tests/frontend_contracts.cjs
.venv/bin/python -m integration.mission_browser --stage after --headed
.venv/bin/python -m integration.mission_browser --stage after --browser firefox
.venv/bin/python -m integration.mission_disposable --headed
.venv/bin/python -m integration.mission_timeline_profile
```

Use the installed Playwright Chromium and Firefox runtimes. The initial legacy baseline was captured before editing the source. The `before` runner now targets the compatibility route, so comparison to the original behavior uses the retained baseline and its local revision. The renderer benchmark build runs from `web/mission-control` with `npm exec -- vite build --mode bench`. Run it from the repository root with `.venv/bin/python -m integration.mission_browser --stage stress --headed`. The disposable PostgreSQL check can serve the same migration-backed fixture to visible Chromium. The actual timeline profile runs the rendered 603-record view in visible Chromium and samples browser process CPU, summed RSS, and JavaScript heap. The report generator checks the retained source hashes, screenshots and logs in `.local-lab/mission-control/` and writes `reports/aria-mission-control-2.html`.
