# ARTEX-inspired Mission Control architecture

Mission Control reads the selected engagement through existing owner-scoped APIs. The asset and exploration views share namespaced record identifiers. The projection adds relationships only for explicit references and exposes unresolved references. PostgreSQL stores the source records. Derived visual state is disposable and reconstructed after reload. Existing process-local topology remains identified separately.

## Delivery order and acceptance

1. **P0-01 through P0-04.** Reuse the application map, team ledger, hypotheses and verification stores. Project stable, unique IDs and explicit edge reasons. A reference is unresolved when its record is absent from the authorized snapshot. Keep observed, inferred, rejected and reviewed states distinct. Exercise filtering, selection and keyboard navigation with a labelled fixture. Verify foreign-session denial and restart reconstruction against retained storage.
2. **P1-01 through P1-04.** Reuse Mission events, task traces and authorized metadata. Extend task and communication views only when recorded data supports them. Read retained HTTP imports without replay, raw capture export or model calls. Verify malformed input, bounded reads and data minimization.
3. **P2-01 through P2-04.** Supplement existing Agents, Infrastructure, Analytics and Investigation surfaces. Record which fields have authority and which are unknown. Preserve task controls, financial admission and evidence review permissions.
4. **P3-01 through P3-04.** Reuse the accessible shell and observational event replay. Run visible Chromium on controlled data, run the offline and isolated service regressions, retain comparative measurements, and generate the mission artifacts.

Each feature is accepted against its cited source records. Missing historical data remains unknown. A browser run with synthetic records establishes interface behavior for that fixture. Model quality and independent review require separate evidence.

## Implemented contracts

- **Asset and exploration.** The browser derives a graph from existing owner-authorized snapshots. Type and record ID identify a node within the selected engagement. Evidence, retained observations and verification records have the same IDs in both views. Capture origins and endpoints group by recorded origin, method and path. Application model claims retain their inferred or stale state. Direct relationships include their field-specific reason. The inspector lists missing references and links to any authorized related record in the loaded snapshot, including records off the current canvas page. Each drawing displays at most 80 nodes. Choose a saved team sequence to inspect historical task, evidence, hypothesis, finding and knowledge revisions in Exploration. Related event nodes use the loaded team journal window. Campaign and authorization history have their own sources and sequence domains in Events.
- **Data authority.** PostgreSQL retains sessions, application map captures, task revisions, catalog evidence, knowledge, findings, authorizations and accounting. The browser constructs a disposable projection and performs no writes. Existing live host topology is a process-local source. Historical values absent from durable records remain unknown. No schema migration was needed.
- **HTTP evidence.** Mission Traffic lists selected Burp history, retained application captures, and owner-imported HAR 1.2 exchanges from PostgreSQL. The list exposes origin, method, timestamps, source-supported sizes, status, and media types. An on-demand request and response inspector shows allowlisted headers and marks credential fields as redacted. For an owner-selected sanitized HAR, body text is absent by default. Selecting reviewed previews retains a bounded JSON or text excerpt after removing credential fields and recognized reflected values. Plain text is rendered as text, including HTML samples. Encoded, malformed, oversized and unretained bodies have distinct states. Existing Burp and application capture bodies retain their original access boundary. [Chrome DevTools HAR export reference](https://developer.chrome.com/docs/devtools/network/reference/#save-all-network-requests-to-a-har-file)
- **Tasks and communication.** Task Center reuses the existing inspector and trace endpoint. Kanban, chronological creation, table and dependency views present stored task states. Communication uses the producer revision and consumer role captured at claim time. The diagram means a recorded dependency snapshot, with model delivery unknown. Prepared review evidence retains that designation. No general message journal was added.
- **Events and replay.** The existing versioned timeline still identifies cursor domains for team and campaign sources. Campaign transitions can include the stored previous state. The browser projects model reservation and terminal settlement entries from eligible accounting timestamps. The replay window is observational and freezes the records available at capture. Its scope depends on the existing source windows.
- **Assurance and accounting.** Agent profiles show attributed retained requests and declared capabilities alongside assignment state. The tool inventory distinguishes declared catalog and adapter registration from worker advertisement and unknown installation/validation. Configured model selection, reservation, provider-reported usage, provider cost receipt and estimates keep their existing meanings. The configured DeepSeek slug is documented by OpenRouter. [OpenRouter model documentation](https://openrouter.ai/deepseek/deepseek-v4-flash)

The Verification and Review panel supports search, filtering, and owner-submitted rejection, blocked, or inconclusive dispositions for applicable retained revisions. The browser passes the expected revision and a stable request ID to the existing review API. Inconclusive and blocked dispositions require a missing-validation description. The server remains responsible for committing the event and enforcing allowed transitions. The browser refreshes after a confirmed acknowledgement and uses the same request ID for an identical retry. Promotion remains governed by the existing evidence lifecycle.

Finding history is available in Investigation and both graph inspectors. It pages the saved team outbox by sequence, projects the recorded state and timestamp, and shows attributed review roles, reasons, named evidence and control references, and snapshot hashes. Unreadable records are counted separately. A missing catalog row stays unavailable even when a historical revision cites its identifier. The history describes past records, while the verification endpoint calculates eligibility from the current retained evidence and scope.

A saved Exploration checkpoint reads the latest ledger revision at or before the selected sequence for each record, within the same engagement and owner. It preserves record IDs and the first and last retained revision timestamps. The API reports missing or ambiguous sequences, unreadable records, and whether its 2,000-record bound was reached. A checkpoint uses recorded decisions and evidence references. The live graph reads current source state.

Asset Graph reads the latest authorized Mission Traffic summary alongside the Application Map. Each saved capture keeps its own ID and source. Mapped captures reference their saved capture ID, and catalog records link only through stored chat source IDs. Canonical HTTP origin and hostname identities group observations. Only a mapped route supplies an endpoint path. Older captures remain accessible through the paged Traffic view. The graph requests HTTP detail when the owner opens the saved inspector, which uses the same authorization and redaction as Traffic. Legacy service summaries lack durable host and evidence attribution.

HAR imports carry deterministic identifier and owner-engagement provenance. An engagement row lock serializes identical imports. Each distinct sanitized projection is immutable. Re-importing with the same preview selection and sanitized content acknowledges the original record IDs. Metadata-only and reviewed-preview imports may produce distinct projections. Reviewed inspection content is encrypted and bound to its capture, engagement, and metadata. Generic chat restoration, model-history reads, and administrator activity exclude those records. Cataloging the ordinary HTTP metadata through the existing evidence API remains possible. The archive itself is held only for parsing, and URL paths, query values, cookies, and original payloads stay outside the saved display records.
